# BillHub 账单导入 App 设计

## 1. 目标与边界

BillHub 是一个以本地账单导入、归一化和个人收支分析为核心的 App。首期支持微信支付与支付宝导出账单，架构上预留银行卡账单能力。

首期目标：

- 导入微信 XLSX、支付宝 CSV，并保存可追溯的导入批次。
- 将不同平台的账单转换为统一的账务事件，而不是只展示原文件列。
- 正确表达成功、退款、关闭、充值、提现、转账等语义，避免把退款或资金搬运当作消费。
- 支持按时间、平台、账户、收支类型、分类和交易对方筛选、聚合与导出。
- 在跨平台账单同时出现同一支付时，识别“可能重复”，但绝不自动删除。

首期不做：

- 自动登录微信、支付宝或银行，不保存平台登录凭据。
- 云端同步、多人账本、自动记账和税务申报。
- 将支付方式推断为可靠的银行流水关联；这只能作为待确认候选关系。

## 2. 现有样本调研

当前目录仅包含两个原始导出文件，均覆盖 2025-10-01 至 2026-09-29：

| 平台 | 文件与编码 | 记录定位 | 明细数 | 核心问题 |
| --- | --- | --- | ---: | --- |
| 微信支付 | XLSX | 第 18 行为表头，第 19 行起为明细 | 1,528 | 顶部有 17 行说明；退款状态包含全额退款和带金额的退款状态 |
| 支付宝 | GB18030 CSV | 第 24 行为表头，第 25 行起为明细 | 514 | 前置回单说明、末尾空列；交易状态与收支字段需要共同解释 |

两份文件都带有平台交易单号和商户单号，应优先作为来源内幂等键。两者还都出现了相同尾号的银行卡支付方式，因此未来银行流水导入时存在跨来源重叠的可能。

已观察到的状态差异：

| 语义 | 微信示例 | 支付宝示例 | 归一化建议 |
| --- | --- | --- | --- |
| 成功支付 | `支付成功` | `交易成功` | 已入账的支出或收入 |
| 退款 | `已全额退款`、`已退款¥x` | `退款成功` | 独立退款事件，金额记为反向现金流 |
| 未完成/关闭 | 无可靠入账状态 | `交易关闭`、`等待确认收货` | 保留原始记录，不计入已入账统计 |
| 资金搬运 | `已存入零钱`、提现等 | `充值成功` 等不计收支 | 中性资金流，不进入消费/收入，但可参与账户余额对账 |

因此，产品不能只按来源文件的“收/支”列求和，也不能仅按交易类型文字判断退款。导入规则必须同时考虑原始方向、交易状态、金额、订单号和关联信息。

## 3. 产品结构

### 3.1 页面

1. **总览**
   - 已入账支出、收入、净现金流、退款、待确认交易。
   - 按月趋势、分类占比、支付账户分布。
   - 默认排除中性资金流；可显式打开“包含充值/提现/转账”。

2. **导入中心**
   - 拖放或选择文件，自动识别平台和格式。
   - 展示识别到的时间范围、记录数、字段映射、错误行、重复数和候选跨平台重复数。
   - 导入前预览；导入后能撤销整个批次。

3. **流水**
   - 统一流水列表：时间、商户/对方、分类、金额、账户、状态、来源平台。
   - 筛选项：账务状态、现金流类型、平台、账户、分类、标签、金额和日期。
   - 允许修改分类、添加标签、合并商户名称、标记为“非本人消费”或“忽略统计”。

4. **对账与重复**
   - 显示来源内重复、跨来源候选重复、未确认状态、无法解析行。
   - 每一个自动规则必须展示命中原因和原始字段；用户可以确认、否决或忽略候选关联。

5. **规则与账户**
   - 商户/关键词到自定义分类的规则。
   - 支付方式规范化为资金账户，例如“某银行信用卡(末四位)”。
   - 配置导入器版本、字段映射和规则启停。

### 3.2 核心统计口径

`已入账消费`：已结算成功的支出减去已确认退款。  
`已入账收入`：已结算成功的收入，退款不并入收入。  
`中性资金流`：充值、提现、账户转存、信用卡还款等，不进入消费/收入指标。  
`待确认`：未完成、关闭、字段不完整或规则无法判定的记录，默认不进入总览。  
`净现金流`：收入 - 支出；展示时要明确它不是账户余额变化，因为中性资金流与跨平台重复可能存在。

## 4. 分层架构

```text
原始文件
  -> 导入批次与文件指纹
  -> 平台解析器 (WeChat / Alipay / Bank)
  -> 标准化与金额、状态语义引擎
  -> 来源内去重、跨来源候选匹配
  -> 人工分类与规则引擎
  -> 账务事件库
  -> 总览、流水、对账、导出
```

推荐采用本地优先的桌面架构：

```text
React + TypeScript UI
        |
Tauri 2 command boundary
        |
Rust domain service
        |
SQLite (SQLCipher optional) + attachment directory
```

选择理由：账单包含敏感身份和交易信息，本地 SQLite 可支持全文筛选、批次撤销和离线使用；Rust 适合做确定性的解析、哈希和金额计算；Tauri 的安装包和资源占用也比把账单交给浏览器后端更合适。金额一律用以“分”为单位的整数 `i64`，禁止浮点数累计。

## 5. 统一数据模型

### 5.1 导入批次

```sql
import_batches (
  id TEXT PRIMARY KEY,
  provider TEXT NOT NULL,              -- wechat, alipay, bank
  parser_id TEXT NOT NULL,             -- alipay_csv_v1
  parser_version TEXT NOT NULL,
  original_filename TEXT NOT NULL,
  file_sha256 TEXT NOT NULL UNIQUE,
  imported_at INTEGER NOT NULL,
  range_start INTEGER,
  range_end INTEGER,
  record_count INTEGER NOT NULL,
  accepted_count INTEGER NOT NULL,
  rejected_count INTEGER NOT NULL,
  warnings_json TEXT NOT NULL
)
```

`file_sha256` 防止同一个文件重复导入；原文件应复制到 App 私有目录并按哈希命名，数据库只保存相对路径。原始文件绝不上传。

### 5.2 统一账务事件

```sql
ledger_events (
  id TEXT PRIMARY KEY,
  batch_id TEXT NOT NULL REFERENCES import_batches(id),
  provider TEXT NOT NULL,
  occurred_at INTEGER NOT NULL,
  settled_at INTEGER,
  event_kind TEXT NOT NULL,            -- payment, refund, transfer, top_up, withdrawal, adjustment
  cash_flow TEXT NOT NULL,             -- expense, income, neutral, pending
  lifecycle TEXT NOT NULL,             -- settled, pending, closed, reversed, unknown
  amount_cents INTEGER NOT NULL,
  currency TEXT NOT NULL DEFAULT 'CNY',
  counterparty TEXT,
  description TEXT,
  category_id TEXT,
  funding_account_id TEXT,
  provider_transaction_id TEXT NOT NULL,
  merchant_order_id TEXT,
  source_row_hash TEXT NOT NULL,
  raw_json TEXT NOT NULL,
  UNIQUE(provider, provider_transaction_id)
)
```

约定：`amount_cents` 始终为正数，方向由 `cash_flow` 和 `event_kind` 解释。退款不是修改原支付金额，而是新建 `event_kind=refund` 的事件；这样可处理部分退款、多次退款和跨结算期退款。

### 5.3 辅助实体

```text
funding_accounts     支付方式映射后的资金账户，例如银行卡尾号或零钱
categories           用户分类树，初期两层即可
classification_rules 关键词、商户和账户到分类/标签的规则
event_links          原支付、退款、候选跨来源重复、人工确认等事件关系
import_issues        行号、级别、字段、错误码、修复建议
```

`raw_json` 保存解析后的原始字段快照，以便规则升级后可重新归一化；绝不以 UI 展示字段覆盖原始证据。

## 6. 导入器接口与规则

每个平台实现同一接口：

```rust
trait StatementParser {
    fn detect(&self, file: &ImportFile) -> Detection;
    fn preview(&self, file: &ImportFile) -> Result<ImportPreview, ParseError>;
    fn parse(&self, file: &ImportFile) -> Result<Vec<RawStatementRow>, ParseError>;
    fn normalize(&self, row: RawStatementRow) -> NormalizeResult;
}
```

### 6.1 微信 `wechat_xlsx_v1`

- 定位表头：匹配完整列集合 `交易时间`、`交易单号`、`当前状态`，不依赖固定行号。
- 解析 XLSX 的日期单元格或文本日期，时区统一按导出说明的 UTC+08:00。
- 幂等键：`provider=wechat + 交易单号`。
- 状态优先级：包含“退款”的状态归入退款语义；`支付成功`归入已结算；其他未知状态保留为待确认并记录告警。
- 支付方式中的 `/` 视为未知账户，不伪造银行卡关联。

### 6.2 支付宝 `alipay_csv_v1`

- 编码探测顺序：UTF-8 BOM、UTF-8、GB18030；解析时保留实际编码。
- 定位表头：首列为 `交易时间` 且包含 `交易订单号`，忽略前置回单说明和尾部空列。
- 幂等键：`provider=alipay + 交易订单号.trim()`；必须去除导出文件中的制表符等尾随空白。
- 状态优先级：`退款成功`为退款，`交易成功`为已结算，`交易关闭`和`等待确认收货`为非入账状态，其他状态进入待确认队列。
- “不计收支”不等于无价值记录，归为 `cash_flow=neutral` 并保留用于资金账户分析。

### 6.3 银行账单 `bank_*_v1`

银行不能按“一个 CSV 解析器”处理。应按银行与导出模板分别注册，例如：

```text
cmb_credit_card_csv_v1
cmb_debit_card_xlsx_v1
icbc_credit_card_xlsx_v1
generic_bank_csv_mapping_v1
```

最低必填字段是交易时间、金额、借贷方向、交易对方/摘要、账户标识、银行流水号或可稳定生成的行指纹。若缺少稳定流水号，只能启用“同文件内弱幂等”，并在预览中明确提示风险。

## 7. 去重与关联

### 7.1 两级处理

1. **硬去重（自动）**
   - 同平台、同交易单号，或者相同文件哈希：拒绝重复导入。
   - 同批次完全相同行指纹：只保留一条并写入导入问题。

2. **软匹配（只给候选，不自动合并）**
   - 适用于微信/支付宝账单与将来导入的银行账单。
   - 以账户尾号、金额、货币、发生时间窗口、交易对方/摘要相似度构成评分。
   - 默认时间窗口为 10 分钟，金额必须相同，且银行卡尾号或归一化商户至少一项匹配。
   - 评分达到阈值只创建 `event_links(kind='possible_duplicate')`，统计仍各自保留；只有用户确认后才在“去重口径”中排除一方。

### 7.2 退款关联

先用平台交易单号、商户订单号和描述字段关联；无法确定时只标记“未关联退款”。不得仅以相同金额自动冲销，以免把两笔独立交易错误抵消。

## 8. 导入流程与失败处理

```text
选择文件
  -> 文件哈希和格式识别
  -> 解析预览
  -> 字段及状态校验
  -> 生成问题列表和导入摘要
  -> 用户确认
  -> 单个 SQLite 事务写入批次、原始行、事件和硬去重结果
  -> 异步构建软匹配候选
```

导入必须是全有或全无。若存在无法解析的行，默认策略是“接受可解析行 + 记录拒绝行”，用户可改为严格模式使任何错误都阻断批次。撤销导入只删除该批次及其未被其他批次引用的关联和附件，用户手工分类规则不应随批次删除。

错误需可操作，例如：

| 错误码 | 呈现给用户的含义 | 建议 |
| --- | --- | --- |
| `HEADER_NOT_FOUND` | 未找到可识别的账单表头 | 确认下载的是账单明细而非截图或汇总文件 |
| `ENCODING_UNSUPPORTED` | 文件编码无法读取 | 重新从平台导出 CSV，或另存为 UTF-8 后导入 |
| `MISSING_TRANSACTION_ID` | 该行缺少稳定交易编号 | 导入为待确认，不能保证重复检测 |
| `UNKNOWN_STATUS` | 平台返回了未识别交易状态 | 保留原始记录，默认不计入统计 |
| `DUPLICATE_FILE` | 文件已完整导入 | 打开原导入批次，或选择替换策略 |

## 9. 数据安全与隐私

- 默认离线运行；不要求账号，不上报交易内容。
- 原始文件、SQLite 和导出结果均保存在 App 私有目录；支持用户选择备份位置。
- 键名、文件哈希、解析器版本和问题码可用于本地诊断；日志默认不记录交易对方、订单号、账号或完整文件路径。
- 可选启用 SQLCipher 或系统钥匙串保护数据库密钥；启用后必须对备份恢复流程给出明确提示。
- UI 中对账号只显示末四位；复制、导出和删除操作需显式确认。
- “删除账本”应先显示影响范围并支持将原文件移入系统废纸篓；不得静默清理用户选择的外部备份。

## 10. 实施路线

### M0：可验证的导入内核

- 建立 Tauri/Rust/React 工程、SQLite 迁移和本地附件目录。
- 实现文件哈希、批次、问题记录、统一事件和交易列表。
- 使用现有两份样本做离线 fixture，测试不保留个人标识和订单号。

验收：同一文件二次导入被阻止；删除批次后事件消失；金额以分存储且无浮点误差。

### M1：微信与支付宝导入

- 实现 `wechat_xlsx_v1`、`alipay_csv_v1`，支持上述动态表头和编码策略。
- 完成预览、状态归一化、退款和中性交易展示。
- 增加导入问题列表和可导出的匿名诊断报告。

验收：现有两个样本都能定位明细表头，记录数与源文件一致；关闭和待确认记录不进入默认支出统计；导入全程可撤销。

### M2：分析与人工校正

- 总览、月度趋势、分类、账户和流水筛选。
- 商户规则、人工分类、退款关联和审计轨迹。
- 来源内硬去重和跨来源候选重复界面。

验收：规则变更只重算派生分类，不改变原始字段；人工确认的重复关系可撤销；每个汇总可追溯到事件列表。

### M3：首个银行适配器

- 选择用户实际使用频率最高的一个银行和一种账单模板，先实现明确命名的适配器。
- 仅当账户尾号、金额、时间和摘要满足严格条件时生成跨来源候选。
- 加入泛化 CSV 字段映射向导，但不把它当成银行适配器的替代品。

验收：银行导入与支付平台导入互不覆盖；候选重复不会自动影响收支统计；解析器版本变更可复现历史导入结果。

## 11. 验证策略

- **单元测试**：金额转换、状态映射、表头定位、GB18030 解码、尾随空白修剪、退款关联和行指纹。
- **属性测试**：任意金额输入不会产生浮点误差；重复解析相同文件获得相同事件键；未知状态不会进入已结算统计。
- **Fixture 测试**：仅保存脱敏后的最小行集，覆盖前置说明、多种退款文本、空字段和关闭交易。
- **数据库测试**：批次写入原子性、幂等约束、批次撤销、人工分类与导入数据的引用完整性。
- **端到端测试**：导入预览、问题展示、确认导入、筛选、撤销和再次导入。

当前样本调研仅验证了文件结构、字段和状态分布；尚未建立实现代码，因此尚未对导入、去重、退款匹配或统计结果做运行时验证。
